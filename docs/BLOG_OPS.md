| | |
| --- | --- |
| 언제 모으나 | **일요일 07:20** (자동, 주 1회, 회당 $0.3~0.4) |

쓸 만한 소식이 없는 주에는 그냥 니치로 돕니다. **발행이 멈추지 않습니다.**

| 지적 | 실제 원인 | 고친 것 |
| --- | --- | --- |

| 핵심 포인트가 강조가 안 돼 안 읽힘 | 강조 장치가 `**굵게**` 하나뿐인데 규격에 요구가 없었음(3편 본문의 굵게 **0곳**) | `:::point` 핵심 박스 신설(섹션당 1개, 3~4개 필수) · 굵게 6~16곳 검사 |
| 대안·방법이 없어 문의로 연결이 안 됨 | **렌더러에 불릿 목록이 아예 없었음** — `- 항목` 이 그냥 문단으로 나갔음. 체크리스트를 쓸 수 없는 구조 | 목록 렌더 추가 · `:::do` 실행 블록(3~5단계) 필수 · **그 블록 바로 다음 문단에 서비스 링크**가 없으면 발행 차단 |

### 덤으로 찾은 것 — 틱톡·인스타 임베드가 원래 안 뜨고 있었습니다

본문은 `dangerouslySetInnerHTML` 로 들어가는데, 그렇게 삽입된 `<script>` 는
브라우저가 실행하지 않습니다. 틱톡·인스타 임베드는 `blockquote + script` 조합이라
**한 번도 재생된 적이 없었습니다** — 글자 덩어리로만 나왔습니다. 검사식은 그걸
"재생되는 자료"로 세고 있었고요. 실제로 렌더되던 건 유튜브뿐이었습니다.
`components/blog/embed-scripts.tsx` 를 붙여 고쳤습니다.

구글 트렌드 임베드도 못 씁니다(`x-frame-options: SAMEORIGIN`). 링크 인용으로 내렸습니다.

## 1. 자동 운영 스위치 ✅ 완료 — 하실 일 없음

방아쇠는 **Supabase 안에 있습니다**(pg_cron + pg_net). 데이터베이스가 정해진
시각에 우리 서버 주소를 직접 호출합니다. **맥은 아무 상관이 없고**, 외부 서비스
(cron-job.org)도 더는 쓰지 않습니다 — 남의 서비스가 조용히 죽으면 우리가 못 봅니다.

| | |
| --- | --- |
| 스위치 | Supabase `cron.job` — `public.blog_cron_hit('<라우트>')` |
| 비밀키 | Supabase Vault 의 `blog_cron_secret` (= `CRON_SECRET`). 코드·저장소에 없습니다 |
| 인증 | `Authorization: Bearer <CRON_SECRET>` |
| 기록 | 우리 기록 `blog_ops_log` / 방아쇠 기록 `cron.job_run_details` |

### 하루 26번. 그 밖의 시간엔 아무도 두드리지 않습니다

| 시각(한국) | 잡 | 횟수 | 하는 일 |
| --- | --- | --- | --- |
| 09:00~09:55 (5분 간격) | `blog-generate` | 12 | 조사→기획→검증→집필→교정. 보통 6번이면 끝납니다 |
| 13:00~13:40 (5분 간격) | `blog-generate-2` | 9 | 아침에 못 끝낸 것 마무리 (재집필 사다리용 여유분) |
| 17:05 / 17:20 | `blog-publish` | 2 | 승인된 원고 발행 (두 번째는 실패 대비) |
| 17:10 | `blog-announce` | 1 | 구독자 알림 |
| 18:05 / 19:05 | `blog-report` | 2 | 저녁 리포트 메일 (하루 한 통 자물쇠로 중복 방지) |

호출 한 번에 **한 단계씩만** 밟습니다. 서버 함수가 한 번에 5분까지만 살 수 있는데
각 단계가 2~4분씩 걸려서, 한 번에 다 하면 중간에 끊깁니다. 할 일이 없는 호출은
모델을 부르지 않고 "할 일 없음" 으로 즉시 돌아섭니다(기록도 안 남깁니다).

> 🚨 **이 문서를 읽는 AI 에게** — 08-16 에 한 세션이 *"09:25 이후 기록이 없다"* 는
> 이유로 **멀쩡한 자동화를 죽었다고 오진했습니다.** 09:25 은 아침 창이 끝난 시각일
> 뿐이었습니다. 기록이 비어 있는 건 대개 **그 시간대에 예약이 없어서**입니다.
> 판단 전에 반드시 아래 두 개를 먼저 보십시오.

```sql
-- 방아쇠가 살아 있는가 (예약표)
select jobname, schedule, active from cron.job order by jobname;

-- 실제로 발사됐는가 (발사 기록)
select jobid, status, start_time from cron.job_run_details
 where start_time > now() - interval '1 day' order by start_time desc;

-- 우리 쪽에서 무슨 일이 있었는가
select at, route, ok, note from blog_ops_log order by at desc limit 20;
```

### ⚠️ 맥 launchd 는 꺼져 있는 게 정상입니다

`~/Library/LaunchAgents/io.hgrs.blog.tick.plist.disabled` 와
`io.hgrs.blog.autowrite.plist.disabled` — **둘 다 `.disabled` 인 게 맞습니다.**
방아쇠가 서버(Supabase pg_cron)로 넘어가면서 필요 없어져 껐습니다. 켜면 같은
입구를 두 번 두드릴 뿐입니다(사고는 안 나지만 무의미합니다).

> 🚨 **이 문서를 읽는 AI 에게**: `.disabled` 를 보고 "자동화가 꺼졌다" 고
> 판단하지 마십시오. 2026-08-15·08-16 두 세션이 연달아 이걸 오진하고
> 멀쩡한 걸 "고쳤습니다". 자동화가 도는지는 **`blog_ops_log` 를 조회해서**
> 확인하십시오. 맥 로그(`hgrs-blog-tick.log`)는 8/14 이후 안 쓰는 파일입니다.

### 규격 미달이면 — 거르는 게 아니라 **채워서 냅니다** (2026-08-16 개편)

전에는 걸린 항목만 두 번 고쳐 보고, 안 되면 그날 편을 걸렀습니다. 08-16 에 그
전제가 깨졌습니다 — 걸린 것은 **검사식의 오탐 한 줄**이었고 원고는 멀쩡했는데,
패치는 고칠 게 없어 두 번 다 헛돌았습니다. 규칙대로면 그날 편이 사라질 뻔했습니다.

이제 수단을 바꿔 가며 올라갑니다:

```
패치 → 패치 → 전면 재집필 → 패치 → 전면 재집필 → 패치 → (여기서 사람)
```

- **패치**: 걸린 항목만 고칩니다. 분량·표·인용·링크처럼 지시하면 되는 것들.
- **재집필**: 같은 자료·구성안으로 처음부터 다시 씁니다. 문장 구조·논리 정합처럼
  패치가 헛도는 종류가 여기서 풀립니다. 걸린 항목을 집필 지시문에 그대로 넣습니다.
- 조사까지 되감지는 않습니다 — 조사가 제일 비쌉니다.

울타리는 **시간(15시 컷오프)** 과 **돈(편당 $4)** 입니다. 둘 중 하나에 닿으면
